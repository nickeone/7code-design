## 2. Voice

**Tone:** direct, senior, pragmatic, business-focused. Partner, not vendor. Never salesy.

**Message formula, every persuasive block:** Context → Value → CTA. Show you understand their world
first. Then the specific outcome, not the service. Then one clear next step.

**Use:** partner · senior engineers · ownership mindset · AI-first / AI-native · production-grade ·
shipped · business outcomes · reliable delivery.

**BANNED — the build fails on these:** leverage · synergy · touch base · circle back · hope this finds
you well · offshore body shop · "resources" (say engineers). Also banned: 🚀 💡 🔥 in headings, and
em-dash-heavy breathless copy.

**Sentence length: 12–22 words average.** This matters. The competitor we are displacing averages 35–45
and it is their weakest habit. Short sentences read as senior. Long ones read as hedging.

**Voice split:** second person owns the problem, first-person-plural owns the fix. "Your team rebuilds
that report every Monday. We automate it." Roughly 1:2 in favour of "we" across a page.

**Never:**
- Invent a metric, percentage, client result, award or search volume.
- Use a client name or number that is not already published on 7code.tech or Clutch (list in §4).
- Copy phrasing from ronins.co.uk. We copy the skeleton, never the words.
- Write two different CTA labels on one page.

## 3. The 13-block skeleton — every money page, in this order

```
hero · trustStrip · diagnosis · successHorizon · proof · cta
whatWeBuild · howWeDeliver · package · cta · pointOfView · faq · close
```

| Block | Job | Rules |
|---|---|---|
| `hero` | H1 contains the exact target keyword, in sentence case. Sub-head names the **person**, not the deliverable. One CTA. | H1 ≤ 12 words |
| `trustStrip` | Proof immediately below the hero, **above the first CTA**. Stats + logos + Clutch rating. | Non-negotiable position |
| `diagnosis` | Describe the reader's situation back to them before mentioning 7code. Three concrete symptoms, then the twist. | The highest-value block. Write it last, after you know the page. |
| `successHorizon` | What good looks like at 3 weeks / 3 months / 12 months. Concrete. | Name a horizon, never "in time" |
| `proof` | Two case studies with a real metric visible, **linked**, service tags as **links** | Two, not three |
| `cta` | Identical label every time | |
| `whatWeBuild` | 5–8 concrete deliverables. Nouns, not adjectives. | |
| `howWeDeliver` | 5–6 bullets, **each one kills a named objection** | This is process copy doing risk-reversal |
| `package` | The productised entry offer, priced as a range, linked to its `/packages/` page | |
| `pointOfView` | The belief statement + **one explicit disqualifier** ("who we are not for") | Every page needs the disqualifier |
| `faq` | 10–12 entries, pre-sales framed, price band in Q1, services named in answers are **links** | Heading: "Questions we get asked before we're hired" |
| `close` | Named human + live calendar + form fallback + reassurance line | |

## 7. File format

One `.mdx` per page in `content/pages/`, `content/packages/`, `content/hub/`.
YAML front-matter conforming to `content/content-spec.types.ts`, then body blocks delimited by
`## BLOCK: <name>`.

Copy the structure of `content/pages/ai-automation-agency-uk.mdx` exactly — it is the approved pattern.

**`status: approved` and `openItems: []` on every file.** Do not leave `[UNVERIFIED]` markers. If you
cannot verify something, write around it using only the facts in §4.

Two build-time constants exist so nothing is hardcoded twice — reference them, don't inline them:
- `REVIEWER_NAME` — the named E-E-A-T reviewer
- `BOOKING_PROVIDER` — the calendar tool behind `/book/*`
