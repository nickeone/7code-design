## BLOCK: diagnosis

**H2:** The agent works until someone else uses it

In the demo it planned three steps, called two tools and produced the right answer. In production it
calls the same tool eleven times in a row. It invents a parameter your API has never accepted. One
support ticket ran for forty minutes and burned four hundred dollars of tokens before anyone noticed,
and the only reason anyone noticed was the invoice.

Underneath that, the real gap: nobody owns the eval suite. There is no graded set of runs, so every
prompt change is a guess and every model upgrade is a leap. When quality drops, the team argues from
anecdotes because there is no measurement to argue from.

Agents are not hard to build. They are hard to operate. The engineering that matters sits in the
scaffolding — step budgets, idempotent tools, typed outputs, approval gates, per-run cost attribution,
and a test harness that fails loudly in CI.

## BLOCK: whatWeBuild

**H2:** What we actually build

- **Tool-calling agents** — typed tool schemas, strict output validation, idempotent side effects,
  retries with backoff, and a step budget that ends a loop instead of letting it run.
- **Multi-agent orchestration** — planner and worker separation, explicit handoff contracts, shared
  state that is written once, and a supervisor that can cancel a branch. We use it where it earns its
  complexity, and we will tell you when one agent would do.
- **Human-in-the-loop approval steps** — a review queue for anything irreversible: payments, external
  messages, record deletion, production writes. With the diff the reviewer needs, not a raw payload.
- **Agent memory and state** — short-term context management, durable run state so a crash resumes
  rather than restarts, and long-term memory with an expiry policy you control.
- **Eval harnesses** — graded run sets built from your own traffic, rubric scoring, regression gates in
  CI, and separate suites for tool-selection accuracy and end-to-end task success.
- **Tracing and cost attribution per run** — every step, prompt, tool call, token count and latency
  recorded, with spend rolled up by feature, by customer and by tool.
- **Guardrails against prompt injection** — untrusted content isolated from instructions, allow-lists on
  tool arguments, output filtering, and least-privilege credentials per tool rather than one shared key.
- **[System integrations](/service/system-integrations) the agent acts through** — the CRM, ERP, ticketing
  and internal APIs, wrapped as tools with sane errors. This is the unglamorous majority of the work.
- **[LLM and agent development](/service/llm-agent-development) and
  [AI product engineering](/service/ai-product-engineering)** as one team, where the agent is part of a
  product rather than a standalone script.

## BLOCK: pointOfView

**H2:** Our point of view

Most systems sold as agents should not be agents. If the sequence of steps is known in advance, a
state machine calling a model at two points is cheaper, faster, testable and far easier to debug.
Autonomy is a cost you pay for genuine branching, and a lot of teams pay it for a workflow they could
have drawn on a whiteboard.

Where autonomy is genuinely warranted, the interesting engineering is not the loop. It is the boundary
around it: what the agent is permitted to touch, what it must ask a human about, what happens on the
fourth identical tool call, and how you measure any of it. We would rather spend week one deleting
autonomy than month six explaining a four-hundred-dollar support ticket.

**Who we are not for:** if you want an autonomous agent because the board asked for one, and the
underlying process is a fixed sequence, we will say so and quote for the smaller thing. Teams looking
for a supplier to build the agent as specified without challenging the design should hire someone else.

## BLOCK: faq

**H2:** Questions we get asked before we're hired

**1. What does agent development cost?** `objection: price`
It depends on tool count, systems touched and how much autonomy the task genuinely needs, but here are
the bands. A two-week paid architecture review is typically **€9,000–€14,000**, the same band as the
[AI-Ready Ops Blueprint](/packages/ai-ready-ops-blueprint). A production build of a full agent-backed
product, a [Production MVP](/mvp-development-agency-uk), usually sits between **€40,000–€90,000** over
three to five months. Ongoing capacity is monthly: a dedicated senior engineer **€6,400–€8,000**, a
dedicated architect **€9,600–€12,800**, a pod of an architect plus two senior engineers
**€22,000–€29,000**. Integration count and approval-workflow complexity move those numbers most. More
detail in [what AI work costs](/hub/what-ai-automation-costs-uk).

**2. Our agent loops and burns tokens. Where do you start?** `objection: failed-before`
With your traces, not your prompts. The usual causes are a missing step budget, tools that return
ambiguous errors so the model retries forever, and no idempotency, so a repeated call looks like
progress. We reproduce the failure against a graded run set, then fix the scaffolding before touching
prompt wording. Prompt edits without an eval set are how teams spend a quarter going sideways.

**3. How do you evaluate an agent, specifically?** `objection: other`
On three levels. Task success against a graded set of real runs, scored by a rubric your team signs
off. Trajectory quality — whether the right tool was selected with the right arguments at each step.
And operational metrics: steps per run, cost per run, latency, and rate of escalation to a human. All
three run in CI. A regression on any of them blocks the deploy.

**4. Which framework do you use?** `objection: other`
We choose per project and we are not attached to any of them. Plenty of production agents are better
served by a plain loop, typed tool definitions and your existing job queue than by a framework that
hides control flow. What we insist on is that the orchestration is inspectable, testable and yours.
Framework choice is written down with the reasoning during the architecture review.

**5. How do you stop prompt injection?** `objection: other`
By assuming it will happen. Untrusted content is separated from instructions and never gets to define
tool behaviour. Tool arguments are validated against allow-lists rather than free text. Each tool has
its own least-privilege credential, so a compromised step cannot reach the whole system. Anything
irreversible goes through human approval. We also add injection cases to the eval suite so defences are
tested on every change, not once at launch.

**6. Can the agent act in our production systems?** `objection: other`
Yes, and carefully. Writes go through wrapped tools with typed inputs, idempotency keys and audit
logging, so a repeated call cannot double-charge or duplicate a record. Destructive and external-facing
actions sit behind an approval step by default. We usually start read-only in production, prove the
trajectory quality on real traffic, then enable writes one tool at a time.

**7. Who actually builds it?** `objection: seniority`
Senior engineers, named before you sign, and the same ones through delivery. The person on your
technical call is the person writing the tool layer. If you want a working session with the engineer
before there is a contract, ask — we prefer it, and it is a faster way to judge us than a deck.

**8. How fast can you start, and when is something live?** `objection: timeline`
Two to four weeks from signed contract to a working team. The architecture review can usually start
sooner. A first agent running against real traffic, read-only, is typically four to six weeks after
that, with writes enabled once the eval numbers justify it.

**9. Who owns the IP?** `objection: ip-ownership`
You do, transferring on full payment. Code, prompts, tool definitions, eval sets and infrastructure
configuration, including anything built on top of our own internal tooling. It is in the standard
contract rather than a premium option.

**10. Will we be locked into you or into one model provider?** `objection: lock-in`
Neither. Everything runs in your cloud account and is documented for handover. Provider calls sit
behind an interface, so switching is a config change the eval suite validates in an afternoon. Some
clients keep us for the next agent; others take it in house after the first release, which we plan for
from the start.

**11. What does support look like after launch?** `objection: after-launch`
Traces, eval runs, cost dashboards and alerts on failure rate, escalation rate and spend per run all
ship with the build. Your team can operate it without us. A support retainer is available and optional,
and the handover documentation is written on the assumption you may not take it.

**12. Is an agent even the right answer for us?** `objection: other`
Often not, and we will say so in the first call. Fixed sequences belong in a workflow with a model at
two steps, which is [AI automation](/ai-automation-agency-uk) work. Question-answering over your
documents is [RAG development](/rag-development-company). A broader AI build is
[AI development company UK](/ai-development-company-uk), and if you would rather add senior capacity to
your own team than outsource, that is [staff augmentation](/staff-augmentation-company-uk). You can see
[how we work](/process) before you talk to us.
